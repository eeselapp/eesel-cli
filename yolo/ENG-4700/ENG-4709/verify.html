What this change is for

ENG-4709

The eesel CLI could already list a workspace's connected integrations, but it couldn't operate on them: no way to see what's connectable, start connecting a new one, or watch a sync — for any of that you had to leave the terminal for the dashboard. This change closes that gap and settles the command names for the integrations group on the ones the ticket specified.

Spec: the ENG-4709 ticket (child of the ENG-4700 CLI audit). This review is the chapter after the build — it checks that what the ticket asked for actually holds against a running server.

What changes for users

Four commands to set up and watch an integration. available lists what a workspace can connect, and for each, its connection options — the ways to connect it (Zendesk, say, offers OAuth, a quick-start form, or messenger). connect <key> --option <type> picks one: a form option connects directly from fields you pass (--field k=v); an OAuth option opens your browser to finish the login and stops there (it doesn't wait). sync triggers a data refresh; sync-status shows each sync's progress.

What must not change (and didn't)

  • integrations list, bare list, --json, --secrets — output unchanged.
  • Old verbs still work as hidden aliases: add for connect, disconnect for remove.
  • Integration secrets stay masked everywhere, including show --json.

Watch this

  • Integrations no longer uses the CLI's shared verbs (add / show / remove, the set every other group uses) — a deliberate call for a human to approve (see PR).
  • connect needs --option when a connector has several; an old add --config script now stops with a clear error instead of doing the wrong thing.

🔍 Review findings — 1 blocker (fixed), plus low notes

This change was checked by a set of independent review passes — one per concern (behaviour, resilience, server load, cost, customer impact, conventions), each done in its own fresh context so no pass graded its own work. Here's what they found.

FixedA misbehaving server made connect dump a stack trace

The shared "let me see the error body" request helper parsed the response as JSON without guarding it. When a server answers a request with a success code but a non-JSON body — a proxy or login page sitting in front of the API, a real misconfiguration — that parse threw and the raw Python traceback escaped. It hit connect (and any command on that helper). This is the same kind of leak that was just fixed for chat.

ran it — reproduced against a local server returning a 200 HTML page (traceback), then confirmed the fix: it now prints one clean line ("the response was not JSON — a proxy or login page?") and exits 1, matching how the strict request helper already behaves. Found and fixed within this verify pass.

LowOld --config / --token connect flags removed (not just hidden)

The build had kept these as "back-compat" flags, but a review pass showed they no longer reproduced the old behavior for the very connectors a script would target. Rather than ship a flag that promises compatibility it doesn't deliver, they were dropped: connect is now field-driven (--field) as the ticket specifies. An old add --config call now stops with a plain "unrecognized argument" error instead of silently doing the wrong thing. ran it.

LowRedundant-sync protection is server-side only

Repeatedly triggering a sync collapses to one run on the server (it returns "already in progress", which the CLI reports honestly). The CLI adds no local guard — acceptable, because it's no worse than scripting the dashboard's own API and the server is the backstop. read it.

Safety squad — each lens ran in its own fresh context:

Resilience — solid after the fix above: unreachable server, 404s, empty/odd responses, malformed --field, headless redirect all give clean exits, no hangs, no tracebacks. ran each.
Operational load — no concern. Each command is 1–2 bounded requests, no fan-out, no retries; the sync-runs feed is server-capped (50 rows + 24h). read + cross-checked the server.
Cost — nothing here adds a new usage-billed call. connect/sync hit the same endpoints the dashboard already drives; the read commands make no model calls. read it.
Customer impact — read paths and the hidden add/disconnect aliases are safe. Some old add --config forms now stop with a clear error instead of connecting — acceptable since these verbs are unreleased; surfaced here so it's a deliberate call. ran each old form.
🙋 Needs a human
  • Approve the command names. Every other command group (documents, agents, mcp, …) uses the same three verbs — add, show, remove. This change gives integrations its own names instead (available, connect, sync-status), so it becomes the one exception. It's the deliberate choice behind this work — and the new connect is also the more correct implementation — but a human should sign off on the divergence before it ships (it's revertable).
    Done when: the team confirms these integration command names are the intended public surface, or asks to fold them back into the shared verbs.
