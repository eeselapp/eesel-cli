🔍 Concerns — 3 low / conventions · plus back-compat for a human

LOW 1 · triggers remove "" — an empty/blank prefix resolves to a single trigger and attempts the delete instead of refusing LIVE

resolve_event_trigger_strict / match_event_triggers · confidence: high · severity: low
The strict resolver refuses when a prefix matches 2+ triggers. But an empty string isn't treated as "matches everything → refuse" — with one trigger present it resolves to that single trigger and issues the DELETE: 
$ eesel triggers remove "" --force
DELETE …/triggers/<id> → 404   (exit 1)
Low severity: --force/confirm still gate it, and with 2+ triggers it refuses. Still, an empty/blank id-prefix should refuse uniformly (agents already special-cases empty to "No agent given") rather than resolve-and-act. (The 404 above is a separate quirk — this event trigger lists but isn't deletable via /triggers/{id}; worth a glance, out of this PR's scope.)

LOW 2 · agents list human output carries an [on]/[off] status column LIVE

confidence: high · severity: low
The default human row is * <id> [on]/[off] <name> [<type>]. A script that parsed column positions out of eesel agents list would read status where it expects name. ENG-4700 fences existing read commands as "must not change in behaviour — only extend," and this is a change to the default human view. Mitigated by the --plain flag (stable, tab-separated) for scripts; human output was never a hard contract, hence low — flagging because it's exactly the class the ticket fenced off.

CONVENTIONS 3 · the documents group is off-pattern — no strict resolution, three resolver styles, three positional names READ

_documents_remove, resolve_document_id, match_document · confidence: high
Every other destructive command resolves a prefix/id strictly and refuses ambiguity; documents remove takes raw exact keys (nargs="+") with no resolution — a typo'd key just no-ops server-side, no local "no match / did you mean". The group also carries two read-resolvers (resolve_document_id vs match_document) and names the same noun three ways across its commands (target / --document-id / keys). Not a safety hole (exact keys, confirm present), but it's the one group that didn't adopt the triad — a public-surface inconsistency worth settling before the namespace hardens.

KNOWN BEHAVIOUR 4 · actions set --config replaces config; skills set merges — different by necessity LIVE READ

_actions_edit / _configure_tool · server tools endpoint has no merge · confidence: high
skills set merges (it PATCHes the config endpoint, which exists for exactly this). The tools endpoint behind actions set has no merge — it replaces the row config wholesale (preserving only the permission keys), and its read enriches config with the tool's schema/tool_data, so a client-side fetch-merge would re-persist that definition blob. So actions set --config writes the action's full config and drops any non-permission setting it doesn't include. This is the server's actual contract (the dashboard form always posts the full schema-derived config), and the --config help + docstring now say so. Worth knowing, not a defect. A true per-field action merge would need a server-side PATCH on the tools endpoint (slack repo) — a follow-up if partial action writes become common.
