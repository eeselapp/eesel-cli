v0.3.0 → v0.4.1   the last customer release 194113b → the release under test a1fa55d in eeselapp/eesel-cli · the ENG-4700 CLI overhaul · re-verified by running the real eesel binary, driving its network code against local sockets, and diffing old-vs-new against the actual v0.3.0 binary

The problem this solves

Between the last release customers installed (v0.3.0) and now (v0.4.1), the CLI's whole command vocabulary was reworked so that similar things are said the same way everywhere. Nouns were renamed and regrouped (documents → files; triggers and schedules gathered under a new automations parent; the old top-level tools became integrations … actions), the write verb became set everywhere (was a mix of edit/update), destructive commands moved to --force (was --yes), six command groups were added (mcp, workspace, skills, automations, billing, settings), and the idea of a remembered "active agent" — an agent being a configured AI assistant in the workspace, the thing that files, skills, and integrations are scoped to — was dropped in favour of naming the agent on each command. On top of all that, two follow-up fixes: moved commands now tell you where they went, and chat now fails honestly instead of dumping a Python traceback or returning a half-finished answer as success.

This is a comprehensive re-verification of that whole upgrade, measured against the last release customers actually run. The most important question for an upgrading customer: do their existing scripts, built on the old command names, still do something safe? (The CLI has no version string in code — its version is the git tag, so "v0.4.1" names the commit a1fa55d, staged pending publish.) ENG-4700 is the parent ticket.

On v0.3.0 (before)

  • A customer scripts document, tools, triggers, instructions, a saved active agent
  • Write verbs are a mix of edit/update; deletes use --yes
  • A moved/removed command → a generic error; a failed chat → a traceback or a fake "success"
→

On v0.4.1 (after)

  • One consistent vocabulary: files, integrations … actions, automations; agent named per command. Old names still work (hidden alias) or point you to the new one
  • set to write, --force to skip a prompt — everywhere
  • Moved command → one line naming its new home; failed chat → clean message + non-zero exit

Verdict: Works — the upgrade ships safely, and a wider sweep found a real fix-list

Verified live by a nine-lens panel — one reviewer per command area plus cross-cutting correctness, conventions, and safety — each working in isolation so none graded its own work, and each diffing the actual v0.3.0 binary against v0.4.1. The upgrade itself is honest and non-destructive: every old v0.3.0 command a customer might have scripted was run against the new binary, and none silently does nothing, the wrong thing, or a destructive thing — each either still works through a hidden alias or fails loudly with a pointer to the new spelling. The two dangerous cases were checked hardest and both hold. The new grammar lets you write a command as eesel agents <id> <verb>, which the CLI rewrites internally into the flag form <verb> --agent <id> — the risk being that an old command, reinterpreted under that rewrite, could land on a different, destructive command the user never typed. It can't: an old agents use remove zendesk can never be rewritten into a destructive integration removal, and an empty agent scope can never become a workspace-wide uninstall. Existing sessions, config, and credentials survive the upgrade untouched. The full test suite is green (646 tests).
But going wider than a spot-check found real defects in the shipped surface — none catastrophic (nothing silently loses data or mass-deletes), but confirmed live: a handful of commands crash with a raw traceback on an odd-but-plausible server response (including the flagship chat), a failed chat stream leaves the local history in a state that re-sends the message next turn, and two spots in integrations … actions act on the wrong or a blank target. This is why the verdict is "ships safely, with a fix-list" rather than an unqualified green: the upgrade path is safe, but the code has a crash-hardening backlog worth clearing before wide rollout.
What changes for users: a single, consistent command vocabulary; old command names either keep working quietly or tell you exactly where they moved; every write is set and every skip-the-prompt is --force; the agent is named per command instead of remembered; six new command groups; and a chat that reports failure honestly.
What must not change (and didn't): a customer's existing v0.3.0 scripts don't silently misbehave — verified command-by-command against the old binary. Destructive commands still refuse a blank or ambiguous target (they name the candidates instead of guessing), and still confirm before acting unless --force is given. On-disk sessions, credentials, and config are read correctly after the upgrade and left byte-for-byte unchanged.
Watch this: two things to fix before a wide rollout — an odd streaming frame can crash chat mid-reply (finding 1), and a failed chat turn corrupts the local session history so the message re-sends next turn (finding 2). Close behind: integrations show crashes on an integration with no recent syncs (finding 3), and disabling an action with a blank name deletes the only action (finding 4).

🔍 Panel findings — a ranked fix-list (none catastrophic; nothing silently loses data or mass-deletes)

Nine independent reviews, each in its own clean context, examining one area or concern apiece. Findings survived a skeptical second look; pure style and anything the test suite already catches were dropped. Numbered for reference. Everything here is a defect present in the shipped surface — it does not change the "upgrade is safe" verdict above, but it is a real backlog. Tags: FIX = should be fixed · DECIDE = a call for a human · KNOW = worth being aware of · DOCS = a documentation correction.

FIX 1 · An odd streaming frame crashes chat mid-reply LIVE

the stream reader, stream_reply · introduced-area: the chat-resilience rewrite touched this code · confidence: high
Chat is the flagship command. While a reply is streaming, if the server sends one malformed frame — a text piece that is empty/null instead of a string, or a data line that isn't an object — the CLI crashes with a raw Python traceback mid-answer. The resilience work hardened the connection-drop and error-event cases but left each individual frame's decoding unguarded. Confirmed end-to-end against a local socket: a good start, then one null text piece, then a traceback escapes. Streaming backends realistically emit empty or odd frames, so this is the top thing to harden.

FIX 2 · A failed chat turn corrupts local history and re-sends the message next time LIVE

send_message · worsened by the overhaul · confidence: high
When a turn starts successfully but the reply then fails (a server error, or a dropped stream), the CLI saves the session with the user's message but no answer. Only one narrower failure path (the request to start the turn being rejected) rolls the message back. Because every turn re-sends the whole local conversation, the next message re-sends that un-answered one. Confirmed live: after a failed turn the session holds a lone user message and sessions show renders two user turns in a row. This is worse than v0.3.0, which crashed before saving anything — so the new honest-failure handling introduced a persistence bug alongside the fix. Whether the re-send double-runs depends on the backend, but the local history is already visibly wrong.

FIX 3 · integrations show crashes on an integration with no recent syncs LIVE

_fetch_sync_runs → _latest_sync_run · new in the overhaul · confidence: high
Showing an integration always looks up its latest sync run. The one sync-runs fetcher is missing the "treat an empty body as an empty list" guard that its siblings have, so an empty or null response makes the code iterate over None and crash. A freshly-connected integration that hasn't synced yet is exactly this shape — so integrations show on a new integration tracebacks.

FIX 4 · Disabling an action with a blank name deletes the only action LIVE

_resolve_action_key · new in the overhaul · destructive-ish · confidence: high
The matcher that finds which action to enable/disable is the one matcher missing the "refuse a blank target" guard that every other resolver in the CLI has. A blank name matches everything, so on an integration with a single configured action it resolves as "unique" and deletes it — and --force skips the confirmation. Confirmed live: an empty-quotes disable removed the sole action. This is the same empty-variable class the reshaper and every other matcher defend against; this one spot was missed.

FIX 5 · Action enable/disable picks an arbitrary instance when a type has several LIVE

_resolve_integration_id · new in the overhaul · confidence: high
When you have more than one integration of the same type, the resolver used by actions enable/disable returns the first match instead of refusing the ambiguity and listing candidates — unlike every strict resolver used by the destructive commands. So the action gets toggled on the wrong instance. Needs two instances of one type to trigger, which is why it slipped, but the fix is to route it through the same strict resolver the rest of the CLI uses.

FIX 6 · Odd or dropped server responses crash many commands with a raw traceback LIVE

the shared HTTP helper http_request; several render functions · root-cause cluster · confidence: high
Two related gaps, both live-confirmed. (a) The shared request helper assumes every 200 body is a JSON object; a 200 that is valid JSON but a different shape (a bare value or list) makes many read commands — billing, workspace, settings, mcp list, tasks, files acl — traceback instead of erroring cleanly. (b) The shared helper catches only the "HTTP error" and "unreachable" exception families; a connection dropped mid-request (a load-balancer reset, a backend restart) is a different family and escapes as a traceback on every non-chat network command. Notably the chat path was hardened for exactly this drop case — but that hardening wasn't carried back to the shared helper the rest of the CLI uses, and the overhaul multiplied how many commands route through it. One catch clause on the shared helper closes most of this class (including findings 1 and 3, which are the same "odd response → crash" shape in other spots).

FIX 7 · chat --task <id> ignores the requested agent LIVE

find_session_by_task · new inconsistency · confidence: high
The agent-match fix — reuse a session only if it belongs to the requested agent — was added to the normal session-picking path but not to the path that resumes a session by task id. So chat --task X --agent B talks to whatever agent that task's session was bound to, not B. Same bug the overhaul set out to fix, left in one code path.

KNOW 8 · tasks analytics can crash after printing half the report LIVE

render_task_analytics · new in the overhaul · confidence: high
The analytics renderer assumes two of its sections arrive as keyed objects; if the server sends them as lists (a natural shape for a distribution) the command prints the first couple of lines and then tracebacks. Same "odd server shape → crash" family as finding 6.

DECIDE 9 · A blank knowledge access-control (ACL) prefix isn't refused before it's sent LIVE

files acl set · confidence: medium (server behaviour unverified)
files acl set <agent> --prefix "" returns success and sends an empty prefix to the server. An empty string is a prefix of every document key, so if the server stores it the agent gets access to everything — the exact over-grant this command is supposed to prevent. The CLI guards blank targets everywhere else but not here. The command does read back and print the server's stored state, so the user isn't misled — but whether the empty prefix is neutralised depends on server-side normalisation we couldn't test (no live stack). Add the same blank guard the rest of the CLI has, and/or confirm the server drops it.

KNOW 10 · Two chat stream residuals — both fail-closed or pre-existing LIVE

stream_reply · carried over · confidence: high
(a) A reply that streams completely and is then followed by a late error event is discarded and the turn marked failed — safe direction (the answer was shown; only persistence/exit treat it as failed), a byproduct of the new honesty gate. (b) A stream that closes cleanly partway through, with no completion marker, still returns its partial text as a success — pre-existing, and indistinguishable from a real clean close because there's no end-of-stream marker the CLI checks. Both hinge on the backend's stream contract; neither blocks the upgrade.

DOCS 11 · Documentation and hints that contradict the shipped surface LIVE READ

README + several docstrings + one test name · independently raised by three lenses · confidence: high
Truth-in-documentation gaps — safe, but a reader is misled: the README quick-start's very first example (eesel agents instructions <id>) is a broken command (it's read as an agent name and errors); the README's files section teaches a hidden alias (read) as the primary verb and never mentions the canonical show; three integrations docstrings still call the removed add/disconnect verbs "hidden aliases" when they're gone; a renamed-verb error suggests the wrong replacement (disconnect → "connect" instead of "remove"); one test's name asserts the opposite of what it checks; and actions list --json prints secrets that actions show --json redacts (matches v0.3.0, worth aligning).

DECIDE 12 · There's no way to turn an agent on or off after creating it LIVE

agents verbs are list/show/create/set/remove · product gap · confidence: high
The agents group has no enable/disable verb, and set doesn't expose the active flag — so once an agent is created there's no CLI way to toggle its on/off state. Internally consistent (nothing claims otherwise), but a customer reading release notes might expect it. A product decision, not a bug.

🙋 Needs a human / to decide

The upgrade is safe to ship. These are the fixes and calls to make; the first two are the ones worth clearing before a wide rollout:

  • [ ] Fix the chat crash + the history corruption (findings 1 & 2). Guard each streaming frame's decode so one odd frame can't traceback the flagship command; and roll back (or otherwise reconcile) the un-answered user message when a turn fails, so the next turn doesn't re-send it. Pass = a malformed frame and a failed turn both leave chat clean and the local history correct.
  • [ ] Harden the shared HTTP helper (findings 3, 6, 8). One catch clause for dropped connections plus an "empty body → empty" guard closes the whole "odd/absent server response → traceback" class across billing, workspace, settings, mcp, tasks, files acl, integrations show, and tasks analytics. Pass = these commands report a clean error and non-zero exit on a dropped connection and a wrong-shape body.
  • [ ] Add the missing target guards in integrations actions (findings 4 & 5). Refuse a blank action name, and refuse an ambiguous integration type instead of picking the first — route both through the strict resolver the rest of the CLI already uses. Pass = a blank disable and a multi-instance type both refuse and list candidates, deleting nothing.
  • [ ] Apply the agent filter to chat --task (finding 7) so resuming by task id honours the requested agent, matching the fix already in the normal path.
  • [ ] Confirm the ACL empty-prefix behaviour (finding 9) — add the client-side blank guard and/or confirm the server neutralises an empty prefix, so an agent can't be granted match-everything access.
  • [ ] Fix the misleading docs (finding 11) — the broken README quick-start example, the hidden-verb-as-primary sections, the stale "alias" docstrings, and the actions list --json secret leak.
  • [ ] Decide on the agent on/off verb (finding 12) and the two chat stream residuals (finding 10) against the backend's stream contract.
