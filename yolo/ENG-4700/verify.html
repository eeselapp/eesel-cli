RESOLVED B2 · triggers remove resolved an ambiguous id-prefix to an arbitrary first match — now strict LIVE TEST

fixed in 44d3e28 · was the one destructive command missed by the strict sweep · flagged by all 3 panel agents
triggers remove was the lone destructive command still on first-match: an ambiguous id-prefix resolved to an arbitrary trigger and deleted it (with --force, no candidate list, no undo). Fix: added a shared match_event_triggers helper + a resolve_event_trigger_strict variant that refuses ambiguity and lists candidates — mirroring the schedules/agents/integrations/mcp pattern; the read-only show path keeps first-match. Removal by full id still works; a new unit test (test_remove_ambiguous_prefix_refuses_without_request) locks the behaviour. Suite: 532 passing.

RESOLVED 3 · tasks analytics sent the wrong token (prod 401) — now uses the workspace token LIVE TEST

fixed in 1313d84, eesel:3220 · confidence: High (not reproducible in prod from here)
The call used token=creds["token"] while every sibling /workspace/tasks call uses workspace_token(creds). The route is @workspace_authenticated (HS256); a prod Auth0 login holds an RS256 token these routes reject, so analytics would 401 in prod while the rest of tasks worked — invisible in dev (the dev token is the workspace token). Fix: one-line change to workspace_token(creds); docstring is now accurate. Still works live in dev ("total tasks: 90"), and a new test (test_uses_workspace_token_not_raw_login_token) locks it.

RESOLVED 4 · README "edit vs set" was inverted — now matches the binary READ

fixed in 4a87359, README.md
The box said edit was canonical for --config ops; the binary makes set canonical and edit a hidden alias. Fix: rewrote the section so set reads as the one canonical write verb (replaces a config object or writes a named field) and edit is documented purely as a hidden back-compat alias.

RESOLVED 5 · "Did you mean?" now fires for integrations <int> actions <typo> LIVE TEST

fixed in 1313d84, _normalize_integrations_argv
The argv normalizer defaulted an unknown first positional to list, burying a typo'd verb as an unexpected argument. Fix: only default to list when there's no verb at all; a present-but-unknown verb is passed through so the actions subparser raises a suggesting error. Verified live: 
$ eesel integrations zendesk actions enabl reply
… invalid choice: 'enabl' (choose from 'list','show','enable','set','edit','disable') Did you mean 'enable'?
Bare actions still lists; valid verbs unaffected. Two new normalizer tests lock the behaviour.
