RESOLVED 1 · eesel agents add was a registered verb that silently did nothing — now dispatches to create LIVE TEST

was: eesel:5131 registered add as a hidden alias of create, but cmd_agents had no add branch → fell through to return 1 · fixed in 2a7c38a · confidence: certain
The alias parsed and set args.agents_cmd="add", but the dispatcher only handled create — so add fell through to return 1: exit 1, no output, no agent. Every other noun's add worked; agents was the lone miss, and no test covered it. Fix: routed add to the create path (if sub in ("create","add")) and added a test that asserts agents add POSTs the same body as create. Re-verified live: 
$ eesel agents add --name "ZZ-add-fix-test" --instructions "verify add alias"
✓ Created agent 'ZZ-add-fix-test' (a4a30021-…)   # exit 0
$ eesel agents list | grep ZZ-add-fix-test
   a4a30021-a34  [on]   ZZ-add-fix-test              # read-back confirms; cleaned up after

SHOULD FIX 2 · skills set --config / actions set --config replace the whole config — and the comment says the opposite READ (server-traced)

eesel:4457–4472 (skills PUT) · eesel:2826–2862 (actions) · server skill_service.py:522–536 · confidence: high
skills set issues PUT /agents/{id}/skills/{skill}/config → server save_skill_config → replace_skill_properties — a wholesale replace. A patch_skill_config that merges (merged = {**existing, **partial}) sits right next to it in the same service file and the CLI doesn't use it. So eesel … skills set <skill> --config '{"one_field": x}' to tweak one setting silently drops every other stored field. The CLI comment at eesel:4463 claims "The server may merge other keys, so we check only the keys we wrote" — false for the PUT it sends, and because the read-back only checks the keys it sent, it can never surface the keys it just dropped. actions set --config has the same shape server-side (only the permission keys are preserved on a config write). Note: the field-level sets (agents set, mcp set, notifications set, workspace set) all correctly merge — the footgun is specific to the two --config-object commands. Fix: point skills set at the existing PATCH endpoint (and correct the comment), or make the read-back diff the whole object and warn on dropped keys.

LOW 3 · triggers remove "" — an empty prefix resolves to a single trigger and attempts the delete, instead of refusing LIVE

resolve_event_trigger_strict / match_event_triggers · confidence: high
The strict resolver refuses when a prefix matches 2+ triggers (good). But an empty string isn't treated as "matches everything → refuse" — with one trigger present it resolves to that single trigger and issues the DELETE: 
$ eesel triggers remove "" --force
DELETE http://localhost:8080/triggers/acb04cf7-… → 404: {"message":"Trigger not found"}
exit=1
Low severity: --force/confirm still gate it, with 2+ triggers it refuses, and the failed DELETE exits non-zero (the server 404 here is a separate quirk — this "other"/event trigger lists but isn't deletable via /triggers/{id}; worth a glance but out of this PR's scope). Still, an empty/blank id-prefix should refuse uniformly (agents already special-cases empty to "No agent given") rather than resolve-and-act.

LOW 4 · agents list human output gained an [on]/[off] column — a read command the ticket fenced as "must not change" LIVE

confidence: high · severity: low
Old row: * <id> <name> [<type>]. New: * <id> [on]/[off] <name> [<type>]. A script that awk'd column positions out of eesel agents list now reads status where it read name. ENG-4700 says the existing read commands "must NOT be modified in behaviour — only extended"; this is a modification, not just an extension. Mitigated for new scripts by the added --plain (stable, tab-separated), but the default human output of an existing read command moved. Human output was never a hard contract, so low — flagging because it's exactly the class of change the ticket fenced off.

CONVENTIONS 5 · the documents group is the odd one out — no strict resolution, three resolver styles, three positional names READ

_documents_remove (eesel:4116), resolve_document_id (3616), match_document (3644) · confidence: high
Every other destructive command resolves a prefix/id strictly and refuses ambiguity; documents remove takes raw exact keys (nargs="+") with no resolution — a typo'd key just no-ops server-side, no local "no match / did you mean". The group also carries two read-resolvers (resolve_document_id vs match_document) and names the same noun three ways across its commands (target / --document-id / keys). Not a safety hole (exact keys, confirm present), but it's the one group that didn't adopt the triad — a public-surface inconsistency worth settling before the namespace hardens.

CLEARED — false alarm workspace set billing-limit token READ (server-confirmed)

flagged as a possible repeat of the tasks analytics wrong-token bug, then traced to the server · confidence: certain
The correctness pass flagged billing-limit for sending creds["token"] (the raw login token) on a /workspace/ route, like the prior analytics bug. But the server route is @requires_auth + @inject_user_id (Auth0/RS256), not @workspace_authenticated (HS256) (server/app/api/workspace.py:169–172). So the raw login token is the correct token here — unlike tasks/analytics, which is HS256 and needed workspace_token(creds). The author's docstring deliberately omitting billing-limit from the HS256 list was right. No change needed.
