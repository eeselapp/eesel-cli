FIX 3 · tasks analytics sends the wrong token — dies in prod READ

eesel:3220, fetch_task_analytics · confidence: High (code + server auth confirmed; not reproduced in prod)
The call uses token=creds["token"]; every sibling tasks call (fetch_tasks :3178, count_tasks :3195, fetch_task_history :3247) uses token=workspace_token(creds). The route POST /workspace/tasks/analytics is @workspace_authenticated (HS256 workspace JWT); a prod Auth0 login holds an RS256 token these routes reject, so the analytics call 401s while the rest of tasks works. Invisible in dev (the dev token is the HS256 workspace token — confirmed working live: "total tasks: 90"). The docstring even claims it "takes the same auth as the rest of the tasks commands" — it doesn't. Prod CLI auth is broadly tracked by ENG-4715, but this is an independent inconsistency the existing helper already solves.
Fix: token=workspace_token(creds) (one line); correct the docstring.

FIX 4 · README "edit vs set" box is inverted — points users at the hidden alias READ

README.md, ### edit vs set section · confidence: High (reproduced vs binary)
The box says edit is canonical for --config/replace ops and set is for single fields. The binary is the opposite: set is the visible/canonical verb for --config ops (agents, mcp, integrations actions, skills) and edit is the hidden alias (hide_subcommands(…, "edit") at eesel:5341/5383/5487/5133). The whole PR exists to establish one canonical vocabulary; the headline doc explaining it contradicts the binary.
Fix: swap the rule of thumb — canonical is set for everything; edit is back-compat only.

FIX 5 · "Did you mean?" misses the integrations <int> actions sub-namespace READ

eesel ~5614, _normalize_integrations_argv · confidence: High (reproduced)
A typo'd action verb (eesel integrations zendesk actions enabl reply) dies with the root-level unrecognized arguments + top-level usage, no suggestion. Root cause: when the first positional isn't a known action verb, the argv normalizer prepends list, so the typo becomes a positional arg to list and never reaches the actions subparser's suggestion handler. Every other group suggests correctly. This is the one place the "everywhere" goal isn't met.
Fix: in the normalizer, pass an unknown non-flag verb through to the actions parser instead of defaulting to list.
