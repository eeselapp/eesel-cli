The eesel CLI describes itself and previews changes

ENG-5030 · P3 of ENG-5025 (make the CLI reliable for an AI agent to drive) · repo eeselapp/eesel-cli · CLI-only · no DB migration

TL;DR — A customer's AI agent has no access to our repo or wiki, so today it has to guess what the CLI can do and hope a mutation is safe. We fix that by building two things the CLI is missing: one function every read routes through (so --json, a new --fields projection, NDJSON-when-piped, and secret-redaction all live in one place), and one function every write routes through (so a new --dry-run can preview any mutation without sending it). On top of those: eesel schema (the whole command surface as JSON, auto-read from the parser) and a committed CONTEXT.md of the invariants an agent can't intuit. Everything is additive — the default human experience does not change.

The problem

When an AI agent (a customer's own Claude Code, or ours in the yolo build→verify loop) is handed the eesel CLI with no access to our repo, wiki, or docs, it wants to discover what the CLI can do and preview a change before making it, so it can plan and act correctly instead of guessing — and not fire an irreversible mutation to find out what a command does.

Three concrete gaps make that impossible today. Each is grounded in the actual code:

  • The agent can't discover the surface without scraping. There is no eesel schema. Discovery = parsing --help text, which is written for humans, omits the API endpoint each command hits, and doesn't machine-express which flags are enums or required.
  • The agent can't preview a mutation. There is no --dry-run. Every write command (agents create, integrations connect, files remove, …) calls the API the moment it runs. An agent's only way to learn what a command sends is to send it.
  • Machine output is inconsistent, and leaks. --json is declared per-subcommand (~34 separate print(json.dumps(...)) sites, plus a few JSON echoes built into f-strings/info()) — there is no global switch, no NDJSON, no way to trim a huge payload down to the fields the agent needs. And because redaction is opt-in per command, only a handful of sites mask secrets today (integrations list/show, actions show, some human-path config views); other --json emitters — e.g. automations triggers show (eesel:2502, whose docstring literally says it "emits the raw payload") — print raw. That is the same class of bug as the ENG-4700 finding where integrations --json leaked access_token/refresh_token — now patched at those integration sites, but the class is still open at every un-redacted emitter.

Grounding: single-file eesel script, argparse-based. ~34 print(json.dumps(...)) emit sites (plus JSON-in-f-string echoes at e.g. eesel:2588, 3420, 3507); every write routes through http_request/http_request_allow_error (no write bypasses it), so one wrapper can capture the whole write set; _redact_secrets exists (eesel:1555) but is applied at only ~7 sites. No global --json; -o/--output is already taken (it's the files export file-path flag). Scored against Justin Poehnelt's "rewrite your CLI for AI agents", this is most of the rubric: runtime schema, dry-run, field projection, a machine-output contract, and a context file.

The ideal — what a magic wand would do

An agent runs one command to learn the entire CLI, gets clean structured output it can trim to what it needs, and can preview any change before committing to it — all without a single line of external documentation. The CLI is self-describing (it tells you what it can do), previewable (it shows you what a change will send), and legible (its machine output is uniform and safe).

The core realisation that shapes the whole build: these are not five unrelated features. The leak, the missing preview, and the inconsistent output are all symptoms of the same root — output and writes are scattered across every command with no shared path. Build the two shared paths and the five deliverables fall out of them. This is solve the family, not the instance: fix the missing shared layer, not each command one at a time.

Do we even need eesel schema — isn't --help enough?

--help is written for a human reading a terminal. An agent scraping it has to parse prose, and it still won't learn the two things it most needs: which API endpoint a command hits, and which flags are closed enums vs free text. A customer's agent has no repo and no wiki — --help is genuinely all it has today. A machine-readable surface it can trust over --help is the force-multiplier that makes every other command usable.

→ Build eesel schema. It's the one command that lets an agent bootstrap the rest.

What does the machine-output contract look like — does piping change what a human sees?

The CLI is dual-audience: humans in a terminal and agents capturing output. The fork is what happens with no --json when output is piped.

A — Implicit NDJSON on pipe (Poehnelt's default). Piped output auto-emits JSON. + Agent never forgets a flag. − A human's eesel agents list | grep bot silently switches from table to JSON — breaks muscle memory.
B — Explicit only. JSON only when asked. + One behaviour, never surprises a human. − No streaming for big lists.
C — Hybrid chosen. No --json → human table always (piping is safe). --json or EESEL_OUTPUT=json → JSON; and when JSON is on and stdout is piped, lists stream as NDJSON (one object per line, so an agent parses a 500-row list line-by-line, not as one giant array). Safe for humans, best for agents.

Env var is EESEL_OUTPUT=json (mirrors the existing EESEL_BASE_URL/EESEL_AGENT precedent). The global switch is --json promoted to the top-level parser; -o/--output is not reused — it stays the files export file path.

How does --dry-run know a POST is a real write? (Some POSTs are reads.)

Keying dry-run on HTTP method alone would be wrong: several POSTs are reads — /workspace/tasks (list), task count, /workspace/tasks/analytics, /tasks/export, /dev/session. Intercepting those would break a plain tasks list. So "the write set" must be named explicitly, not inferred from the HTTP verb.

A — Intercept per-command after body assembly. − Scattered across every write site; easy to miss one.
B — A write_request() choke point chosen. Tag each real mutation (the set enumerated below) to route through one wrapper; dry-run lives there. Reads and read-backs use the ordinary http_request and always run (dry-run still needs to resolve an agent id or fetch existing keys). Bonus: this is an audited registry of every write the CLI performs — one place that lists them all, useful for P5 safety and for schema's endpoint annotations.

Behaviour: on a write with --dry-run, print the resolved request as JSON and exit 0 without calling. The first pending write is shown; the rare multi-write command stops at the first (documented). Reads still execute, so the resolved body reflects real resolved ids.

Why is redaction on by default now, and can't that break a script that read a token out of --json?

Today redaction is opt-in, so a secret-bearing payload leaks unless the command author remembered to mask it — that's the ENG-4700 class. Once every read routes through emit(), redaction is applied in one place, by default. Revealing raw secrets stays behind a gate: --secrets and a sysadmin/impersonator login. That gate exists in exactly one place today — integrations list (eesel:2834, reveal = --secrets and _is_sysadmin); the design generalises it to every command via emit() (so e.g. integrations show, which currently has no --secrets flag and always masks, gains a consistent reveal path).

The one edge: if a script today parsed a raw secret out of a non-integration --json payload, it now gets *** unless it's a sysadmin passing --secrets. This is a deliberate security fix, not a regression — but it's named here so it's a conscious call, not a surprise. Non-secret fields are untouched; the vast majority of --json output is byte-identical.

Should --fields support nested paths, or just top-level keys?
Top-level only for v1 chosen — --fields agent_id,name,is_active. Covers the context-window goal (trim a fat agent/task row to the columns the agent needs) with a trivial, predictable implementation.
Nested dotted paths (config.cron) — deferred. More surface, fiddly semantics on lists-of-objects; add only if a real loop needs it. An agent can always fall back to full --json + its own filter.

Unknown field name → omitted from the projected object (not an error), so an agent can request a superset safely.

How we build it — the eng plan

The whole change is additive and CLI-only: no server work, no DB migration, no new dependency (stdlib-only holds). The risk is concentrated in PR 1 (the emit refactor touches all 34 read sites); the rest are small additions. The existing test_eesel.py suite is the safety net for the refactor.

PieceConcrete shape (grounded in the code)
emit()New helper near the output helpers (eesel:159). Signature ~ emit(payload, *, fields=None, reveal=False). Resolves format from --json/EESEL_OUTPUT + sys.stdout.isatty(); applies --fields; applies _redact_secrets unless reveal; emits pretty JSON to a TTY, NDJSON per-list-element when piped. Route all JSON emission through it — the ~34 print(json.dumps(...)) sites and the JSON echoes built into f-strings/info() (e.g. eesel:2588, 3420, 3507), or those keep leaking after the refactor.
write_request()Thin wrapper over http_request/http_request_allow_error for each write in the enumerated set above. Checks a module-level DRY_RUN (set from a global --dry-run): if set, print the resolved {method,url,body} via emit() and exit 0.
eesel schemaNew top-level subcommand + cmd_schema. Recurse the build_parser() tree (subparsers, actions, choices, required, help). Enrich with a small hand-kept {command → endpoint} annotation map (the write_request registry supplies most of it). Output via emit() so --fields works on it.
--fields / --dry-run / --jsonGlobal flags on the top-level parser so they apply uniformly; existing per-command --json keeps working (sets the same value).
--paramsGlobal-ish flag consumed by create/set handlers: parse JSON, merge under the explicit flags (explicit flags win), feed into the same build_*_body helpers.

Drafted CONTEXT.md — the invariants an agent can't intuit

Content is cheap to align on now and expensive to discover wrong after a build, so the actual words are drafted here (final polish at build):

  • Scope an agent first. Almost every command acts on one agent. Set it with --agent <id-or-name> or EESEL_AGENT; a single-agent workspace needs neither.
  • Ask for machine output. Pass --json (or EESEL_OUTPUT=json). Piped list output is NDJSON — parse one object per line. Trim big payloads with --fields a,b,c.
  • Discover, don't guess. eesel schema --json lists every command, flag, enum, and endpoint. Trust it over --help.
  • Preview before you write. Add --dry-run to any mutation to see the exact request it would send, with no call made.
  • Secrets are masked. --json shows *** for tokens/passwords. Raw values need --secrets and a sysadmin login — a normal agent never sees them.
  • Auth model. eesel login (browser Auth0) for a human; eesel link <url> for a worktree against a branch env. (A headless EESEL_TOKEN is the sibling piece P4/ENG-5028 — document it here once it lands.)
  • Exit codes. 0 = success, 2 = usage error, non-zero otherwise = failure. (The typed taxonomy — auth vs not-found vs rate-limit vs validation — is P2/ENG-5027; this section documents whatever exists when P3 builds and is updated when P2 lands.)

Acceptance criteria

What's new or different — each verified against the running CLI (branch deploy or login --dev), not just a passing test:

  • Output contract. eesel agents list in a terminal prints the human table (unchanged). eesel agents list --json prints a pretty JSON array. eesel agents list --json | cat prints NDJSON — every line parses as one agent object. EESEL_OUTPUT=json eesel agents list matches --json. Evidence: capture each, parse it.
  • Redact-by-default. A previously-raw emitter that carries a secret — e.g. automations triggers show --json on a trigger whose config holds an access_token — now shows *** with no --secrets. On a command with the reveal gate (integrations list --json --secrets): a sysadmin sees the raw value, a non-sysadmin still gets *** (gate holds). Evidence: the masked field and the revealed field side by side.
  • Field projection. eesel agents list --json --fields agent_id,name returns objects with only those keys. An unknown field name is silently omitted, not an error.
  • Self-describing. eesel schema --json lists every subcommand present in build_parser, each with its flags (name, required, enum choices) and the API endpoint it hits. Spot-check: a chosen enum flag's choices match the parser; every command in the schema resolves to a real handler.
  • Preview a write. eesel agents create --name Probe --dry-run prints {method:"POST", url:".../agents", body:{...}}, exits 0, and creates nothing — read back with eesel agents list and confirm Probe is absent. Repeat the pattern for a DELETE (agents remove … --dry-run leaves the agent) and a config write. A POST-read (tasks list) is not intercepted by dry-run — it still returns data.
  • Raw params (if built). eesel agents create --params '{"name":"Probe"}' --dry-run resolves the same body as the equivalent flags; an explicit --name overrides the params key.
  • Bootstrap test. A fresh agent given only CONTEXT.md + eesel schema --json output (no other docs) can list agents as JSON and dry-run a mutation correctly. human-look read the transcript once — does the doc actually teach the loop?

What must not change — the regression surface, named explicitly:

  • Every command's no-flag human output is byte-identical to today (tables, colours on a TTY, stderr prefixes).
  • Existing per-command --json still works and — for non-secret payloads — emits the same shape. integrations list/show already redact; unchanged.
  • -o/--output on files export still writes to a file path (untouched by the contract).
  • Writes without --dry-run behave exactly as today, including confirmations and GET read-backs.
  • The interactive chat / REPL and chat --json (shipped in P1) are unaffected.
  • Exit codes stay 0/1/2 — P3 does not change them (that's P2's job).

Not a test plan — unit and contract tests are expected as part of the build, unprompted; the AC grades the user/agent-visible outcome.

Who it affects · what we're committing to

Customer impact

  • New users / existing users: additive — new flags and a new schema command; the default human experience is unchanged. The one deliberate behaviour change: --json now masks secrets by default across all commands (a security fix; the edge is a script that parsed a raw non-integration token out of --json — it now needs sysadmin --secrets).
  • Deployed agents (the eesel agents themselves): none. This is the CLI client, not the agent runtime — no agent config, prompt, or behaviour is touched.

Commitments we'll live with

  • The output contract — when JSON, when NDJSON, the EESEL_OUTPUT name, the global --json. Agents branch on it; it can't be reshuffled later.
  • The eesel schema output shape — agents will trust it over --help.
  • The --fields / --dry-run / --params flag names and semantics.
  • Redact-by-default with --secrets+sysadmin to reveal — a security contract.
  • CONTEXT.md as the canonical location for agent invariants.

Notes & sequencing

  • P2 (ENG-5027) owns the typed exit-code taxonomy. CONTEXT.md's exit-code section documents whatever exists when P3 builds; if P2 lands first, document its taxonomy — coordinate so the doc isn't wrong.
  • P4 (ENG-5028) adds EESEL_TOKEN. CONTEXT.md's auth section mentions it once landed.
  • The write_request() registry pairs naturally with P5 safety work — build it cleanly so P5 can lean on it.
  • No irreversible path and no migration here, so no build-stop human gate. Verify focus: the --secrets reveal gate can't be bypassed by a non-sysadmin.
