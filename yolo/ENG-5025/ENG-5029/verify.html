ENG-5029 — safe for an agent to drive the CLI unattended & in parallel

P5 (the fifth build slice of ENG-5025) · repo eeselapp/eesel-cli · branch kira/eng-5029-…parallel-safe-sessions · picks up from the kickoff plan — this checks that what it specified holds.

The problem this solves

The eesel CLI is now driven by AI agents — a customer's own Claude Code, and ours — often several at once, sometimes crashing and retrying, sometimes passing an id the model invented. Three behaviours were fine for one human at a terminal but bite an unattended, parallel driver:

Before — safe for one human

Which conversation is "active" lives in one shared file (current.json, the pointer). Two parallel runs fight over it — one run's turn lands in the other's conversation.

Session files are written in place. A crash mid-write leaves a truncated file; the next read fails to parse it and the whole conversation is silently lost.

A hallucinated id (../../workspaces/x, control chars, ? # %) flows straight to the API; every failure looks like exit 1, so the agent can't tell "you sent garbage" from "the server broke".

After — safe for an agent fleet

An opt-in EESEL_SESSION env var pins a run to its own session — it reads and writes only that session and never touches the shared current.json pointer. (It mirrors the existing EESEL_BASE_URL, which pins a run's server target the same way.)

Every write is atomic (write a temp file, then rename it into place). A reader — or a crash — only ever sees a complete file. No conversation is dropped.

A malformed id is rejected locally with exit 5 and a message naming what was wrong, before any network call. Well-formed ids and keys are untouched.

Does it work?

YES

All 14 acceptance criteria pass, exercised against the real ./eesel binary (plus a mock backend for the chat path) by a panel of fresh-context reviewers who did not write the code. The panel also found one redundant piece of machinery (a file lock that guaranteed nothing the atomic rename didn't) — removed — and one place where validation now accepts fewer values than before that's worth a human's eye (see below).

The single thing to look at: validation now rejects an agent name or schedule title that contains / ? # % — you'd have to target those by id instead. This is what the spec's rules ask for, but it's a real change for anyone whose agent is literally named e.g. Sales/Support. Details in "Needs a human".

What changes for users

  • Agents (new): per-run session isolation via EESEL_SESSION; distinct exit codes an agent can branch on.
  • Everyone: a genuinely malformed id now fails locally with exit 5 instead of hitting the API and returning a server error.
  • Session/credentials files can no longer be corrupted by a crash or a race.

What must not change (and didn't)

  • Plain interactive eesel chat keeps one sticky session across turns.
  • new / sessions use / list / show still read & repoint the pointer.
  • Well-formed ids and keys reach the API unchanged.
  • _redact_secrets still masks token fields; its tests pass.

🙋 Needs a human (1)

Confirm it's OK that validation now accepts fewer values on the name/title commands. Several commands let you name a thing by its human name or title instead of its id — agents <name> show, automations schedules fire <title>, mcp show <name>. The new validation checks that typed value before looking it up, so a name/title containing / ? # % is now rejected with exit 5 — e.g. an agent named Sales/Marketing or a job titled Q1 50% can no longer be addressed by name (its id still works).

Why it's shipped this way: the plan's coverage table (§4 — the list of CLI arguments that become part of an API URL) classes these as opaque ids, and criteria AC7/AC9 require rejecting traversal and ? # % on id arguments. The typed name/title is matched inside the CLI and never itself becomes part of a URL (only the looked-up id does), so rejecting it there buys no extra safety — it's purely failing fast. The call: keep the strict rule as specified, or relax validation for the by-name lookups (accepting that AC9 is weaker there). I did not relax it unilaterally because it's a product decision the plan already made one way.
Pass = tick this box to accept it as-is, or open a follow-up to loosen the three by-name lookup commands.

🔍 Problems found — 4 fixed, 1 flagged for a human

1. FIXED — the file lock was redundant machinery. The change originally took an fcntl advisory lock around each write. Two reviewers proved (8-process crash-stress, and again with locking forced off) that the atomic temp-write + os.replace with a unique temp name already guarantees no torn file — 0 failures either way. The lock wasn't held across the read-modify-write (load → append → 600s HTTP turn → save), so it prevented no lost update either; the plan itself accepts a benign last-writer-wins on the pointer. Meanwhile it cost an unbounded set of hidden .lock files that delete_session orphaned. Removed the lock and the fcntl import; kept _atomic_write. This deviates from the plan's "under a short file lock" wording — it delivers the plan's actual guarantee (no dropped conversation) with fewer moving parts. Re-verified: crash-stress still 0 torn; no .lock/.tmp files left behind. Fixed in b95b298.

2. FIXED — EESEL_SESSION was validated after a network call. The pin was only checked inside ensure_current_session, which runs after the agent lookup. So a bad pin with the backend down exited 1 (after a wasted request) instead of 5. Now validated at the top of cmd_chat. Re-verified live: EESEL_SESSION=../creds with an unreachable backend → exit 5, no network. Fixed in b95b298.

3. FLAGGED — name/title matchers reject legit values with / ? # %. See "Needs a human" above. Still open on purpose: it's a product decision the plan already made (reject on id surfaces), and the affected values (a name/title carrying a URL metacharacter) are unusual, with the id as a working fallback. Not silently changed.

4. FIXED — a failed os.replace could strand a temp file. _atomic_write now unlinks the temp and re-raises on failure, so a failed write leaves the existing file intact and nothing behind. Covered by a new unit test. Fixed in b95b298.

5. FIXED — a ticket id in a README comment. Removed. Fixed in b95b298.
