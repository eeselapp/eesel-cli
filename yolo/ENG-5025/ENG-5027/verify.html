Picks up from the kickoff plan — this checks what section 4 specified actually holds.

The problem this solves

eesel is the command-line tool for the eesel AI product. An AI agent driving it unattended — in a container or CI, with no human and no terminal attached (a "headless" or "non-TTY" run) — couldn't trust the outcome. A command that did nothing could report success; a real failure gave no machine-readable reason. So the agent had to guess whether to retry, re-authenticate, fix its input, or give up.

Terms used below: a typed exit code is the number the process returns ($?), now chosen by failure class so an agent can branch on it without parsing the error text. The shared HTTP helpers are the internal functions every command routes its API calls through — sending failures through them is what gives most commands their typed code. A redirect / browser-OAuth connect is a connector that authorises by sending the user to a web page, which can't happen when there's no browser.

Today (before) chat with no message → drops into a REPL, hits end-of-input, exits 0 having sent nothing.
files read with no target → prints "Cancelled." (nothing was cancelled).
integrations connect on a browser-OAuth option → prints a URL and exits 0 having connected nothing.
Any API error — 401, 404, 429, 500 — all collapse to exit 1.
After this change On a non-interactive terminal those three commands fail with a clear reason and exit 6 instead.
Failures carry a typed exit code by class: 3 auth · 4 not-found · 5 rate-limit · 6 validation · 7 server. 0/1/2 unchanged.
The interactive experience for a human at a real terminal is untouched.

Does it work?  Yes — with three cheap fixes worth making first

All six acceptance criteria pass, verified against the running CLI: typed exit codes driven end-to-end through a stub server for every HTTP status class, and all three non-TTY guards observed firing (and correctly not firing on a real terminal). 713/713 unit + contract tests pass.

The single biggest thing to look at: the files read guard is placed after a network call, so a headless files read with no target against a briefly-down server exits 7 ("retry later") instead of 6 ("fix your call") — telling the agent to retry a call that can never succeed. Nominal case (server up) exits 6 correctly; this is an edge the AC didn't pin. One-line hoist fixes it.

What changes for users

  • A headless agent gets an honest outcome + a typed code it can branch on, with no special knowledge.
  • Three deliberate failure-path changes: OAuth connect run headless now exits 6 (was 0); chat/files read with no argument on a non-TTY now error with 6 (was 0 / "Cancelled."); a failing API command's code changes from 1 to its typed class.
  • --no-input is now a documented, discoverable flag.

What must not change (and didn't)

  • On a real terminal, chat/files read/connect still open the REPL / picker / browser hand-off — ran it live (pty) for connect; test-covered for the pickers.
  • Successful commands still exit 0; argument-usage errors still exit 2 via argparse — ran it live.
Watch this: the typed-code contract is applied unevenly. The chat streaming path and a few local-input errors still exit generic 1, so an agent that branches on 3/5/7 gets 1 in those corners. Mostly in-scope per the plan — but two sites contradict their own code comments (see Problems #2). And a confirmed collateral regression: two best-effort background lookups now leak a red ✗ error banner they used to swallow (Problems #3).

🔍 Problems found (survived pressure-testing) — 1 medium behavioural, 1 scoped, 1 confirmed regression, 2 low

#1 MEDIUM · still open observed live files read no-target guard fires after a network fetch

In cmd_files_read, candidates = agent_documents(...) (an HTTP call) runs at eesel:4943, before the non-TTY guard at eesel:4965. So for a headless files read with no target:

  • Against a briefly-unreachable / 5xx server, the fetch exits 7 (server, "retry later") before the guard can return 6 (validation, "fix the call"). Observed live: with the backend down, ./eesel files read </dev/null returned 7. The agent's own permanent usage bug is mislabeled as transient, so it retries forever.
  • On an empty workspace it returns 0 at eesel:4946 before ever reaching the guard.

Why still okay to ship: the AC ("no target, non-TTY → 6") passes in the nominal case (server up), which is what was tested and locked. This is an edge the AC didn't pin. Fix: hoist the guard above the fetch — it doesn't use candidates. The chat guard is already placed correctly (pre-network); this makes files read match. connect's guard also runs after its definition fetch, but that fetch is genuinely required to know the option is a redirect — acceptable.

#2 MEDIUM · scoped, 2 sites open chat / streaming path never emits typed codes

The one-shot chat path collapses every failure to generic 1: return 0 if reply is not None else 1 (eesel:3758), and send_message/stream_reply use bare sys.exit("string") on unreachable/non-JSON (eesel:1793, 1814, 1897) which yields exit 1. So eesel chat "hi" against an unreachable server exits 1 while eesel agents list exits 7; a chat turn rejected 401/429/500 exits 1, so an agent never learns to re-auth/back-off/retry from a chat turn.

Why largely okay to ship: the plan (section 3, "how wide does the mapping reach") explicitly scoped typed codes to the shared HTTP helpers and says "leave everything else at 1." The chat SSE path is hand-rolled urllib, not those helpers. But: the two URLError sites at eesel:1814 and :1897 carry comments that say "exit cleanly like the shared http_* helpers" — and those helpers now return 7, so the comments are now false. Cheap, low-risk to route those two through fail(EXIT_SERVER, …); the deeper "chat turn 401 → 3" is a larger scope call (accept, or file a follow-up).

#3 MEDIUM · confirmed regression · still open reproduced silent best-effort lookups now leak a ✗ error banner

_latest_sync_run (eesel:2927) and find_task_row (eesel:3998) wrap an HTTP call in try: … except SystemExit: return None to degrade silently when a secondary lookup fails. Before, http_request failed via sys.exit(string), whose message was never printed because the SystemExit was caught. Now fail() calls err(msg) before sys.exit(code), so the red banner is written even though the exit is still swallowed.

Reproduced directly: a swallowed 500 in _latest_sync_run now emits ✗ GET …/v2/sync-runs → 500: {"error":"boom"} to stderr while still returning None. User-visible on the success paths of eesel integrations status, eesel tasks show, and eesel tasks cost — the command still works but prints a scary line it never used to. Cosmetic (no exit-code or functional change), but it defeats the intended silent degradation and is pure collateral. Consider having those two helpers suppress stderr around the swallowed call.

#4 LOW · pre-existing http_fetch has no timeout handler despite its "mirrors http_request" docstring

http_request/http_request_allow_error catch (TimeoutError, socket.timeout) → EXIT_SERVER, but http_fetch (eesel:1112) catches only HTTPError/URLError. socket.timeout is not a URLError subclass, so a slow server on files read/export escapes as a traceback (exit 1), not 7. The diff didn't touch this clause, but it now routes http_fetch through typed codes and its docstring claims parity — so the claim is inaccurate.

#5 LOW · scope-acknowledged local-input errors are typed inconsistently

The three new guards return 6, but sibling local-input errors still return 1: _integrations_sync invalid --type (eesel:3088), _integrations_connect missing required --field (eesel:3051), and _parse_field_args malformed field. The README says "6 = bad/missing local input," so an agent gets 6 for some local-input errors and 1 for others. The plan scoped the mapping to "the clear cases," so this is acknowledged, not a regression.

Safety squad (each lens ran — presence is the point)

  • Resilience — fine. fail() adds no traceback surface; code_for_status is total over any int (unclassified → generic 1, never an exception); guards only call sys.stdin.isatty() and short-circuit before network. No new crash path.
  • Operational load — fine, one caveat. The CLI adds no requests and does no retrying (the chat guard removes a round-trip). Caveat: 429 → "back off and retry later" but no Retry-After is surfaced, and all 5xx/timeout lump into 7 "retry later" — a naive agent could retry a permanent 500. Inherent to a status taxonomy; the non-retryable classes (3/4/6) are split out sensibly.
  • Cost — clean. No metered/paid call added or changed; pure client-side mapping + TTY refusals.
  • Customer impact — the real watch item. Exit-0-on-success is preserved everywhere (scripts checking -ne 0 keep working). The sharp break: a failing command's code moved off 1, so a script whose failure branch is if [ $? -eq 1 ] now misses a 404/500 and routes it into its success branch. Also OAuth-connect and no-arg chat/files-read in CI flip from "green" 0 to red 6. All correct fixes, but under-documented — see "Needs a human" #3.
